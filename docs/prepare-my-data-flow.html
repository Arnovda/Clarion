3 Full sequence diagram

Every API call in order. The frontend drives the entire flow — each step waits for the previous one.

sequenceDiagram
    participant U as 🖥️ Browser
    participant B as ⚙️ Backend
    participant C as 🤖 Claude API
    participant E as 🐍 ETL Service
    participant PG as 🐘 PostgreSQL
    participant W as 📁 Warehouse

    rect rgb(239, 246, 255)
    Note over U,C: Step 1 — Propose (SSE stream)
    U->>+B: POST /products/propose-stream {connectionId}
    B->>PG: Read source_tables + source_columns
    B->>+C: Claude: analyse source, propose data products
    loop Streaming
        C-->>B: thinking tokens
        B-->>U: SSE: {type: thinking, text: "..."}
    end
    C->>-B: Final proposal JSON
    B-->>-U: SSE: {type: done, proposal: {...}}
    end

    rect rgb(240, 253, 244)
    Note over U,PG: Step 2 — Create records
    U->>+B: POST /products/build-proposed {proposal}
    B->>PG: INSERT data_products, star_schemas,
data_product_sources, data_product_dependencies
    B->>-U: {products: [{name, id}, ...]}
    end

    rect rgb(254, 252, 232)
    Note over U,W: Step 3 — Ingest source data (NEW)
    U->>B: GET /semantic/tables?connectionId=X
    B->>U: [{table_name: "customers"}, ...]
    U->>+B: POST /ingestion/ingest {connectionId, tables}
    B->>PG: UPDATE connections SET ingestion_status='running'
    B->>+E: POST /ingest {source_type, config, tables}
    E->>W: Read source DB → write Delta Lake (Parquet)
    E->>-B: {warehouse_path, results: [...]}
    B->>PG: UPDATE connections SET warehouse_path=...
    B->>PG: UPDATE ingested_tables SET delta_path=...
    B->>-U: {ok: true, warehouse_path: "..."}
    end

    rect rgb(245, 243, 255)
    Note over U,W: Step 4 — Wave 1: Reference data (per topic, parallel)
    par Design Customers
        U->>+B: POST /products/1/design-stream
        B->>PG: Read source_columns for assigned tables
        B->>+C: Claude: design star schema
        C-->>B: thinking + schema JSON
        B->>PG: INSERT star_schemas, product_tables, product_columns
        C->>-B: Done
        B->>+C: Claude: generate transformation SQL per table
        C->>-B: SQL strings
        B->>PG: UPDATE product_tables SET transformation_sql=...
        B-->>-U: SSE: {type: done}
    and Design Calendar
        U->>B: POST /products/2/design-stream
        Note over B,C: Same flow (silent)
    end

    par Build Customers
        U->>+B: POST /products/1/run-full
        B->>PG: Read product_tables WHERE transformation_sql IS NOT NULL
        B->>PG: Read connections.warehouse_path
        B->>W: DuckDB: delta_scan() → create views from ingested tables
        B->>W: DuckDB: execute transformation SQL
        B->>W: DuckDB: COPY TO parquet (output)
        B->>PG: UPDATE product_tables SET status='success', row_count=...
        B->>-U: {results: [{table, status, row_count}]}
    and Build Calendar
        U->>B: POST /products/2/run-full
        Note over B,W: Same flow (silent)
    end
    end

    rect rgb(255, 241, 242)
    Note over U,W: Step 5 — Wave 2: Analytics data (depends on wave 1)
    Note over U,C: Same design + build pattern
but fact tables can JOIN to
dim tables from wave 1
    end

    U->>U: ✅ "All done! Your data is ready to query."

6 Auto-repair loop

When transformation SQL fails, the backend automatically asks Claude to fix it (up to 2 attempts).

flowchart TD
    A["Execute transformation SQL
(all tables, DAG order)"] --> B{"Any tables
failed?"}
    B -->|No| Z["✅ Return results"]
    B -->|Yes| C["Collect failed tables
+ error messages"]
    C --> D{"attempt < 2?"}
    D -->|No| Z
    D -->|Yes| E["For each failed table:"]
    E --> F["Read product_columns
(expected output schema)"]
    F --> G["Call Claude:
repairTransformationSql()
with error + SQL + expectedColumns"]
    G --> H["Save corrected SQL
to product_tables"]
    H --> I["Re-run ONLY
repaired tables"]
    I --> J["Merge results back"]
    J --> B

    style A fill:#dbeafe,stroke:#3b82f6
    style Z fill:#d1fae5,stroke:#10b981
    style G fill:#fefce8,stroke:#eab308
    style E fill:#fee2e2,stroke:#ef4444

Bug: repair validates against wrong columns

The repair prompt receives product_columns (what Claude designed) as the "expected" schema. If Claude designed a column called stad during star schema design, the repair loop sees stad as the expected column — it doesn't know the source column is actually called city. So the repair reinforces the original mistake instead of fixing it.

Fix: also pass source column names

Add the source_columns from the ingested tables as additional context to the repair prompt. Then Claude can see: "The error says 'stad' not found. The source column is 'city'. Replace stad → city."

Error 1 — No warehouse path

Where: transformationRunner.ts:152

When: Every topic's build phase

Root cause: ETL service not running or ingestion never triggered

Fix: Ingestion step added before transformations. Must hard-gate if ETL fails.

Error 2 — Serialization Error

Where: transformationRunner.ts:189-205

When: DuckDB creates views from ingested delta files

Root cause: Corrupted parquet from a previous failed ETL run

Fix: Re-ingestion overwrites the corrupted files. run-full alone doesn't help.

Error 3 — Column "stad"

Where: transformationRunner.ts:266 (DuckDB exec)

When: Executing Claude-generated SQL

Root cause: Stale/wrong source_columns → Claude picks wrong name at design time

Fix: Refresh source metadata before design + pass source columns to repair prompt.
